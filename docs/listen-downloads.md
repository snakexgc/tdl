# 监听下载

入口在“下载管理”之后，路径为 `/listen-downloads`。新增或编辑规则时，按名称、用户名或 ID 搜索聊天，可筛选群组、频道、机器人和用户并多选。抽屉中的修改先作为草稿；确认抽屉后，点击页面“保存”统一提交，取消不会修改运行规则。

规则保存到 `components.download.listen.values.rules`，成功落盘后立即生效，保存失败或修订号冲突保留原运行规则和页面草稿。其他设置和组件启停仍需重启。首次启用及停用后再次启用从当次启用时间开始，改名保持进度；重叠规则合并，任一启用规则选择评论即可开启该频道的评论跟踪。

只监听收到的消息。下载沿用当前实际生效的大小、扩展名、目录、命名和下载器设置，页面显示过滤条件及设置入口。自动监听逐条处理相册消息，下载结果进入现有下载管理。每个监听来源下面直接列出全部任务，显示文件名、消息、评论标识、下载状态、进度、速度和错误；停用或删除规则后仍可查看历史任务，刷新页面不会丢失。

监听下载与表情触发共用 `account.telegram.values.file_limit` 的同时下载文件数和 `account.telegram.values.dc_pool_size` 的每个 DC 连接上限，不为监听另设下载预算。表情触发的任务优先取得空闲文件名额及 DC 分片名额，共享调度器中同级任务按原队列顺序处理，已经开始的文件和已授予的分片继续运行。优先级保存在媒体源记录中，监听重放不会降低表情任务的优先级；aria2 的表情任务插入等待队列前部，重试保留优先级。下载队列位置使用 [aria2.addUri 的 position 参数](https://aria2.github.io/manual/en/html/aria2c.html#aria2.addUri)。

“下载频道评论中的视频”默认关闭，只作用于频道帖子的评论区。纯文字原帖也建立跟踪；评论按实际讨论线程关联，仅下载视频，包括按普通文件上传的视频。群组回复已属于群消息范围，无需这个开关。

评论结合实时更新与约每 5 分钟补查，一个共享调度器最多同时执行两路工作，并错开请求、遵守限流等待。补查在原帖发布时间满 24 小时后停止，此后收到可关联的实时评论仍处理。未加入讨论群但能够读取评论时依靠补查；推送范围以 Telegram 实际提供的更新为准。评论线程的关联方式见 [Telegram 评论机制](https://core.telegram.org/api/discussion)。

账号独立 KV 保存版本化启用时间、历史游标、线程、待处理事件和提交结果。恢复连接最多回查最近 24 小时，每页事件持久化后才推进完整检查的游标；实时推送不推进该游标。按账号、来源类型和 ID、消息 ID、媒体身份去重，编辑后出现新媒体可再次下载。明确未接收的提交退避重试；结果不明先核对下载器任务，无法确认时显示“待确认”，保留记录以避免重复提交。停用来源停止新增任务与补查，已经接收的任务继续由下载管理处理。

实现与配置参考见 [开发基准](baseline.md)、[界面设计](../design.md) 和 [配置 schema](configuration.md#downloadlisten--监听下载)。
